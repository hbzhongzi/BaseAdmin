# MemoryAdmin 框架优化与开发规划

## 1. 文档目的

本文档用于规划 MemoryAdmin 从“可运行的后台模板”逐步演进为“可复用、可维护、可安全上线的后台基础框架”。

本文档描述目标、顺序、边界、验收方式和风险。当前已开始落地阶段 0 和阶段 1 的基础项；未明确列为已完成的内容仍属于规划，不得视为已具备生产能力。

### 当前已落地项

- 前端认证 token 状态集中管理，路由守卫和布局退出状态保持响应式。
- 请求层支持超时、外部取消、401/403 识别、token 刷新和并发刷新复用。
- 登录表单增加提交 loading 和原生回车提交。
- PHP 认证错误对 401 返回 HTTP 401，管理员模型隐藏密码和 token 字段。
- 登录失败增加基于 IP/用户名的基础 15 分钟限流窗口。
- 环境类型声明合并，提供 `.env.example`，依赖锁文件不再被忽略。
- 增加单管理员权限及关联表增量 SQL，认证 `me` 接口返回权限编码。
- 增加 PHP `AdminPermission` 中间件、前端 `v-permission` 指令和当前管理员权限状态。

## 2. 当前基线

当前模板已经具备以下能力：

- Vue 3 + TypeScript + Vite + Vue Router + Element Plus 前端基础框架。
- `/admin/` 子路径部署配置。
- 登录、退出、token 请求头注入和前端路由守卫。
- ThinkPHP 风格的管理员登录、刷新、退出和当前用户接口示例。
- `admin_user` 基础管理员表和 bcrypt 密码校验。
- 5 种布局预设、5 种主色、深色模式、侧栏折叠和用户偏好持久化。
- `doce/` 文档索引、认证约定、数据库说明、主题说明、部署说明和静态风格画廊。
- `npm run build` 前端构建检查和 `php -l` PHP 语法检查。

当前仍属于模板阶段，主要缺口集中在：

1. 认证安全还没有达到生产级别。
2. 单管理员权限基础已经具备，但权限管理页面、动态菜单和业务路由接入仍需完善。
3. 请求层缺少更完整的 token 生命周期审计、错误上报和业务重试规范。
4. 依赖锁定、代码质量、自动化测试和 CI 尚未形成完整闭环。
5. 移动端交互、错误页、空状态和加载状态仍需要统一设计。
6. PHP 示例与具体业务系统之间还缺少标准扩展边界。

## 3. 总体目标

### 3.1 产品目标

- 新项目可以通过配置快速确定 API 地址、默认主题和部署路径。
- 管理员可以稳定完成登录、刷新、退出、账号管理和权限访问。
- 业务开发者可以按统一方式添加页面、API、菜单、权限和数据表。
- 用户可以在不同布局、主色和深色模式之间切换，并保持偏好。
- 生产环境具备清晰的部署、回滚、监控和故障排查路径。

### 3.2 工程目标

- 前端代码结构稳定，页面、请求、主题和认证职责分离。
- 后端接口统一响应信封、HTTP 状态、鉴权中间件和错误处理。
- 所有重要行为都具备可验证的测试或发布检查项。
- 框架使用文档与代码同步维护，`doce/README.md` 是框架使用说明入口；优化规划统一维护在 `middoce/`。

### 3.3 安全目标

- 不在前端或日志中泄露密码、token、密钥、SQL 和堆栈。
- 认证失败、token 过期、账号禁用和权限不足都能被明确区分和审计。
- 登录具备限流、防暴力破解和异常行为记录能力。
- 生产环境默认使用 HTTPS，并具备明确的 Cookie、CORS、CSRF 和安全响应头策略。

## 4. 设计原则

### 4.1 先稳定基础能力，再扩展业务

认证、请求层、权限模型、数据访问和错误处理属于基础能力。业务页面必须建立在这些能力稳定之后，避免每个业务模块重复实现登录判断、分页、权限和异常提示。

### 4.2 单一事实来源

- 路由只在路由模块维护。
- 菜单由菜单配置或权限数据驱动，不在多个组件重复声明。
- 主题预设只在 `src/theme/presets.ts` 登记。
- 主题变量只在 `src/theme/tokens.css` 维护。
- API 字段和响应结构以接口文档为准。
- 数据库结构以迁移脚本或版本化 SQL 为准。

### 4.3 安全边界由服务端决定

前端菜单隐藏、路由守卫和按钮禁用都只是用户体验措施。真正的身份认证、权限集、数据范围和敏感操作校验必须在 PHP 服务端完成。

### 4.4 每个阶段都必须可验收

每个阶段必须同时定义：目标、范围、交付物、测试方式、回滚方案和完成标准。没有验收标准的“优化”不进入开发排期。

## 5. 分阶段路线图

建议分为 6 个阶段推进。每个阶段可以独立发布，但后续阶段依赖前置阶段的结果。

```text
阶段 0 资产与基线整理
        ↓
阶段 1 认证与请求层生产化
        ↓
阶段 2 管理员权限集与菜单权限
        ↓
阶段 3 业务模块开发规范化
        ↓
阶段 4 质量工程与自动化发布
        ↓
阶段 5 可观测性、性能与长期治理
```

## 6. 阶段 0：资产与基线整理

### 目标

明确当前模板的可发布基线，清除依赖、文档和目录结构上的不确定性。

### 任务

#### 0.1 依赖和锁文件

- 决定使用 npm、pnpm 或 yarn 作为项目唯一包管理器。
- 保留并提交对应 lock 文件。
- 验证干净目录下安装依赖可以成功。
- 检查 `package.json` 与 lock 文件依赖版本一致。
- 记录 Node.js、npm 和 PHP 的最低版本。

#### 0.2 环境配置

- 明确 `.env.development`、`.env.production` 是否提交到仓库。
- 提供 `.env.example` 作为配置模板。
- 将所有前端公开变量与后端密钥明确区分。
- 记录 `VITE_API_BASE_URL`、`VITE_DEFAULT_LAYOUT`、`VITE_DEFAULT_PRIMARY` 的合法值。

#### 0.3 目录和产物

- 确认 `src/` 只保留 TypeScript/Vue 源文件。
- 确认 `dist/`、缓存、临时文件和编辑器文件不会被提交。
- 明确旧业务页面和旧编译产物是否永久移除。
- 为 PHP 示例与目标项目的复制边界补充说明。

#### 0.4 文档基线

- 框架使用统一从 `doce/README.md` 进入，优化任务从 `middoce/README.md` 进入。
- 检查所有文档链接和文件路径。
- 删除不存在的工具、技能或命令描述。
- 给每个接口、数据库字段和环境变量补充负责人或维护范围。

### 交付物

- 可复现的依赖安装流程。
- `.env.example` 或等价配置说明。
- 目录和提交边界说明。
- 文档链接检查结果。

### 验收标准

- 在干净环境执行安装和构建成功。
- 依赖版本由 lock 文件确定。
- 新开发者阅读 `doce/README.md` 即可启动和使用项目；需要了解演进计划时再阅读 `middoce/README.md`。
- 不存在含糊的环境变量、部署路径或过期文档。

## 7. 阶段 1：认证与请求层生产化

### 目标

将当前“可登录”升级为具备过期、刷新、异常、限流和安全存储能力的认证基础设施。

### 任务

#### 1.1 认证协议统一

确定并冻结以下内容：

- 登录请求字段。
- 登录成功和失败响应结构。
- HTTP 状态码和业务码的职责。
- 认证请求头或 Cookie 方案。
- token 有效期、刷新有效期和撤销规则。
- 账号禁用、删除、锁定和密码修改后的 token 行为。

#### 1.2 token 存储策略

生产环境优先评估 HttpOnly、Secure、SameSite Cookie 方案；如果继续使用前端 token，必须明确 XSS 防护、过期时间、撤销机制和存储风险。

后端不建议明文保存长期 token。可改为保存 token 哈希，查询时对请求 token 做同样的摘要处理。无论采用数据库还是 Redis，都必须保证签发、校验、刷新和退出使用同一套策略。

#### 1.3 登录安全

- 增加 IP 和账号维度的登录限流。
- 增加失败次数和临时锁定策略。
- 统一错误提示，避免账号枚举。
- 记录登录成功、失败、退出、刷新、禁用和异常 IP。
- 对管理员登录增加可选验证码、二次验证或单点登录扩展点。

#### 1.4 前端请求层

规划统一请求客户端，至少包含：

- 请求超时。
- AbortController 取消请求。
- JSON、FormData、文件下载三类请求处理。
- HTTP 错误和业务错误统一转换。
- 401 自动刷新 token。
- 并发请求只允许一个刷新任务，其余请求等待结果。
- 刷新失败后清除认证状态并跳转登录。
- 防止登录、退出和刷新请求互相递归。

#### 1.5 当前用户上下文

统一管理当前管理员信息，包括：

- 管理员 ID。
- 用户名和显示名。
- 权限集（当前版本不区分角色）。
- 权限编码。
- 账号状态。
- token 过期时间。

### 交付物

- 版本化认证接口文档。
- 认证状态管理模块设计。
- token 轮换和撤销策略。
- 登录限流和审计策略。
- 请求层错误码规范。

### 验收标准

- 正常登录、退出、刷新和当前用户查询全部成功。
- 过期 token 只能触发一次刷新，刷新失败后正确回到登录页。
- 账号禁用后旧 token 立即或在约定时间内失效。
- 未授权请求返回正确 HTTP 状态码。
- 密码、token 和堆栈不出现在响应和普通日志中。

## 8. 阶段 2：管理员权限集与菜单权限

### 目标

在暂不引入多角色的前提下，完善管理员直接绑定权限集、菜单声明和业务路由鉴权。

### 推荐数据模型

```text
admin_user            管理员
admin_permission      权限点
admin_user_permission 管理员-权限关系
admin_login_log       登录审计（规划）
admin_operate_log     操作审计（规划）
```

### 任务

#### 2.1 权限粒度

至少规划三种权限：

- 页面权限：能否访问某个页面。
- API 权限：能否调用某个接口。
- 操作权限：能否执行新增、编辑、删除、导出等动作。

后续如有必要，再增加数据范围权限，例如全部数据、部门数据、本人数据。

#### 2.2 权限编码

权限编码必须稳定、唯一、可读，例如：

```text
user:list
user:create
user:update
user:delete
user:export
```

前后端都使用权限编码，不依赖中文名称或前端路由名称判断权限。

#### 2.3 菜单和路由权限

- 当前阶段菜单先由前端配置集中维护，登录后使用 `me.permissions` 做展示过滤。
- 后续再增加菜单字典接口；在此之前不把前端菜单配置误认为服务端安全边界。
- 路由进入前进行页面权限校验。
- 按钮使用统一权限指令或组合式函数。
- 未授权访问显示 403 页面，不直接跳转登录。

#### 2.4 管理员管理

规划管理员管理能力：

- 新增管理员。
- 修改密码。
- 重置密码。
- 启用和禁用。
- 绑定权限集。
- 查看登录记录。
- 强制下线。

### 交付物

- 权限数据模型和迁移脚本。
- 权限编码表。
- 管理员、权限接口文档。
- 前端菜单和按钮权限规范。
- 403、404、500 等错误页面设计。

### 验收标准

- 不同权限集登录后看到的菜单不同。
- 没有 API 权限时，直接调用接口也会被服务端拒绝。
- 隐藏菜单不能绕过服务端权限。
- 管理员禁用或强制下线后不能继续使用旧会话。
- 权限变更有审计记录。

多角色 RBAC（`admin_role`、`admin_user_role`、`admin_role_permission`）暂列为后续扩展，不作为当前版本的实现前提。

## 9. 阶段 3：业务模块开发规范化

### 目标

让后续业务模块按统一方式开发，避免每个页面自行实现请求、列表、分页、表单和权限。

### 前端模块标准结构

建议每个业务模块按以下方式组织：

```text
src/
├── api/user.ts
├── views/user/UserList.vue
├── views/user/UserForm.vue
├── components/user/
└── types/user.ts
```

### 列表页标准能力

- 查询条件。
- 分页。
- 排序。
- 加载状态。
- 空状态。
- 错误状态。
- 批量选择。
- 批量操作。
- 权限控制。
- 导出任务。

### 表单页标准能力

- 字段类型和校验规则。
- 新增、编辑、查看三种模式。
- 提交 loading。
- 重复提交保护。
- 服务端校验错误回显。
- 离开页面未保存提示。
- 成功后刷新列表或返回来源页。

### 后端模块标准结构

建议固定分层：

```text
Controller  参数接收、权限检查、响应转换
Logic       业务流程、事务、领域规则
Model       数据访问和模型关系
Validate    参数校验
Resource    输出字段转换
```

控制器不直接堆积复杂 SQL 和业务流程。分页、排序、筛选、批量操作要使用统一基类或公共服务。

### 交付物

- 一个完整的标准业务模块示例。
- 列表、表单、详情、删除和导出的接口规范。
- 前端页面模板和后端控制器模板。
- 通用分页、错误、空状态和加载状态组件。

### 验收标准

- 新增一个普通 CRUD 模块不需要复制认证、分页和错误处理代码。
- 页面、API、菜单和权限可以通过统一约定互相对应。
- 所有写操作具备输入校验和重复提交保护。
- 列表接口限制最大分页大小和可排序字段。

## 10. 阶段 4：质量工程与自动化发布

### 目标

将“人工验证能运行”升级为“提交后自动验证、可回滚发布”。

### 任务

#### 4.1 静态检查

- TypeScript 类型检查。
- ESLint。
- Vue 模板检查。
- PHP 语法检查。
- PHP 静态分析。
- Markdown 链接和格式检查。

#### 4.2 测试分层

单元测试：

- token 解析。
- 主题预设校验。
- 权限判断。
- 分页参数处理。
- 表单校验。

接口测试：

- 登录和退出。
- token 刷新。
- 权限拒绝。
- 管理员禁用。
- 业务 CRUD。

端到端测试：

- 登录流程。
- 路由守卫。
- 主题切换。
- 布局切换。
- 业务新增、编辑、删除。
- 浏览器刷新和深层链接。

#### 4.3 CI 流程

建议流水线：

```text
安装依赖
  ↓
类型检查 / Lint
  ↓
前端单元测试
  ↓
PHP 语法 / 静态检查
  ↓
接口测试
  ↓
生产构建
  ↓
生成构建产物与版本信息
```

#### 4.4 发布和回滚

- 产物带版本号或提交 SHA。
- 构建产物不可变。
- 发布前执行数据库备份。
- 数据库迁移必须可追踪。
- 保留上一版本静态资源和后端代码。
- 明确前后端兼容窗口。

### 验收标准

- 合并请求不能绕过必需检查。
- 构建失败不会发布到生产。
- 能够回滚到上一版本。
- 关键认证和权限用例全部自动验证。

## 11. 阶段 5：可观测性、性能与长期治理

### 目标

让系统出现问题时可以定位，让规模增长后仍保持可维护性。

### 可观测性

- 统一请求 ID。
- 记录 API 耗时、状态码和错误码。
- 登录、权限拒绝、敏感操作单独审计。
- 前端上报未捕获异常和资源加载失败。
- 监控 PHP 慢请求、数据库慢查询和缓存命中率。
- 日志中禁止记录密码、完整 token 和敏感个人信息。

### 性能

- 减少全量图标注册。
- 路由和大型业务模块懒加载。
- 使用 `manualChunks` 或等价方案拆分产物。
- 表格采用服务端分页和必要字段返回。
- 图片和文件使用独立资源策略。
- 对频繁查询增加缓存，但必须定义失效规则。

### 长期治理

- 每个业务模块记录负责人和依赖。
- 依赖定期升级并执行安全扫描。
- 每月检查过期文档和失效链接。
- 每次新增主题、接口、表结构都同步更新文档。
- 重大变更保留迁移说明和回滚方法。

## 12. 推荐版本路线

### v0.2：基线稳定

- 锁定依赖。

## 14. 禁止事项

- 不在没有迁移和备份方案的情况下修改生产表结构。
- 不在前端代码中写入后端密钥、数据库密码或固定 token。
- 不用前端隐藏菜单代替后端权限校验。
- 不直接在控制器中复制复杂业务逻辑。
- 不通过删除错误处理来“解决”接口报错。
- 不在没有构建、语法检查或测试记录的情况下宣称完成。
- 不在 `doce/` 新增优化规划；优化规划统一放入 `middoce/`，框架使用说明统一从 `doce/README.md` 进入。

## 15. 最终完成定义

当以下条件全部满足时，才可以认为框架达到生产基础版本：

- 依赖可复现安装，构建和检查由 CI 自动执行。
- 认证具备安全 token、刷新、撤销、限流和审计能力。
- 权限、菜单和按钮权限由服务端统一控制；多角色 RBAC 作为后续扩展。
- 前端请求、错误、加载、空状态和权限状态统一处理。
- 主题、布局和移动端体验经过实际浏览器验证。
- 数据库迁移、备份、发布和回滚流程明确。
- 关键功能拥有自动化测试。
- 文档、接口、数据库和代码结构保持同步。
